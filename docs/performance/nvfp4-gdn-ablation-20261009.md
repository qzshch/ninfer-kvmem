# NVFP4 调度与非 CP GDN 融合：四组完成报告

四组均已完成单路/双路测试。结论如下：

- NVFP4：中等长度 residual 矩阵耗时减少约15–27%；补充完整时间线确认，48,061-token冷输入没有执行513–1023的新调度区间，所以没有长Prefill收益。
- GDN：T1024组件耗时增加21.1%；仅GDN的单路48K冷请求TTFT增加2.15%、整请求增加2.92%，双路TTFT增加0.22%。补充计数器及求逆顺序对照见第11节。本轮不作为日常默认。
- 两项同时启用：单路/双路长输入 TTFT 相对 B0 的耗时减少分别为 -0.57% / +0.14%。不能把 NVFP4 的组件收益直接推广为整体收益。

## 1. 实际改了什么

NVFP4：将 A4 residual 投影在 513–1023 token 时切换到已有的 256-token、3-stage TMA 路径。≤512 和 ≥1024 token 的路线不变，权重格式、K16 E2M1/E4M3、激活量化和 FP32 residual/SwiGLU epilogue不变。这是已验证的形状调度调整；本轮未实现跨 lane 投影打包。

GDN：一个 kernel 内设置两个 128-thread 准备组、四个共享 packet 槽，以及一个 256-thread 全历史状态续算组。准备 Q/K、log gate、控制矩阵时，另一组执行前一个块的续算。≥256 token、Hv≥16 进入融合；其他形状保留 prepared/recurrent 路线。Qwen 27B 使用 D=128、Hqk/Hv=16/48，宽 value tile=64。

GDN 保留 16-token 数学分块、原来的归一化 epsilon 和 BF16 舍入边界、FP32 控制矩阵及 FP32 master state；不截断历史、不裁剪 log gate、不改为 FP16 求逆。融合候选将单位下三角矩阵求逆改为 FP32 分块代入，数学上求解同一个矩阵，但 FMA 顺序改变，因此没有逐 bit 相同的承诺。

GDN 的状态转移仍为：α=exp(g)，δ=β(v−αS·k)，S←αS+δ⊗k，o=scale·S·q。FlashInfer 提供了共享内存和准备/续算融合的参考方向；没有直接套用其不同 gate 表示和精度路径。

## 6. 正确性与验收边界

NVFP4 两个 residual 真实形状5120×6144、5120×17408，含255/256/257、511/512/513、1023/1024/1025边界，采用独立 FP64 oracle、guard 和输入保留检查。组合组额外捕获并重放 T128/513/1025 的 Graph。SwiGLU 原有独立数值测试通过。

## 8. 最终选择与后续方向

保留NVFP4的已验证形状调度；GDN融合留在独立和组合实验分支，日常默认禁用。准备/续算、shared、寄存器和同步的补充证据见第11节；后续考虑packet复用或更低同步成本，在有组件和完整请求正收益之前不直接合入默认。

本轮未完成跨lane GEMM打包。初轮四组没有硬件计数器；第11节仅补采GDN组件，并未新测NVFP4矩阵或整个阶段的DRAM/Tensor瓶颈。没有把HiCache、量化或草稿模型更换混入四组。三轮的小差异属于观察值，不能保证所有上下文与任务都取得同样收益。

## 11. 补充根因诊断：覆盖率、融合成本、求逆顺序

本节回应“长Prefill为什么不变、GDN完整请求结果及是否无损、HiCache是否隔离”。补充采样不是新一轮速度验收；第4、5节的未采样三轮成绩继续保留。新增私有证据为 `research/2026-10-09-kernel-root-cause/evidence`，公开汇总追加在本报告JSON的 `root_cause_followup`。

### NVFP4：长请求根本没有进入新调度区间

对冻结B1二进制采集一条48,061-token冷请求的完整CUDA/NVTX时间线，保持单lane、36K/256K、FP8、KVMem、vision、DFlash2 K7、chunk1024、Host4GiB及Native隐式缓存，HiCache关闭。输出上限16，采样时间不用于吞吐排名。追踪覆盖完整冷Prefill与512-token查询回放。

实际 `prefill.chunk` 为46个1024，以及445、508、4、503、5、4。总计48,573，正好是48,061输入加512回放。513–1023的块数为**0**。1024块沿用原来的TMA内核，≤512沿用原来的小块路线；这次只修改residual投影的513–1023入口，所以在该请求上的直接优化覆盖率为零。

此前用“48K的大多数块是1024”解释得不完整：名义余数957也没有成为一次957投影。Program在检索query_begin、前缀capture及rewrite frontier处拆块，之后再回放查询尾部，导致实测尾块都≤512。因此不是已有15–27%的组件收益被其他瓶颈吞掉，而是这个负载没有执行有收益的形状。该结论限这条固定48K输入和当前chunk/检索/缓存配置，不保证所有长请求都没有513–1023尾块。

下一步应优化实际1024形状及对应格式的投影，再做单/多lane整请求对照；真正跨lane打包仍是另一项尚未实现的工作。不应通过更改分块来人为制造“当前长Prefill已提升”的成绩。

| DRAM吞吐（峰值百分比） | 5.31% | 0.062% | 0.066% |
| barrier等待/issued instruction | 10.24 | 0.94 | 2.70 |
| short-scoreboard等待/issued instruction | 1.48 | 0.74 | 1.93 |
| local spilling requests | 0 | 0 | 0 |

原因有三层：

1. 原prepare可在token块×head上并行，3072个CTA覆盖170个SM；融合把准备塞入仅96个持续运行的状态CTA，每CTA只有两个128-thread准备组。两种状态续算均只有0.56个SM wave，融合并未补足未使用的SM。
2. D128/value-tile64有两条value分片。融合对每片分别准备相同的QK、gate和控制矩阵，准备packet从每head×chunk一次变为两次。省全局packet同时引入重复数学、更多组内barrier和生产/消费mbarrier；反映在融合barrier与short-scoreboard等待上。计数器没有把各项额外成本分成精确微秒，不能声称某一项独占全部回退。
3. 原15.5MB中间工作区的后续读取基本来自L2，DRAM远未饱和。把它移到shared并不等于节约同等时长的显存搬运。融合shared增加约48%、线程翻倍，Tensor活跃却下降；active warps由16.66%增至32.92%，所以本例也不能简单解释成“occupancy降低”。不存在local spill证据。

L2命中率原CSV约99.99%，少数多pass派生值略高于100%，视为采样一致性限制，未裁剪原数据。等待指标只在issue未饱和的背景下解读。参考：[Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)。

在B1完整轨迹中，原prepare+recurrence内核累计约0.250s，完整Prefill/回放窗口5.632s。GDN范围包含投影，不能把该范围都当成GDN本体。融合本体回退被其他阶段稀释，因此组件+21%不会成为整请求+21%；也不据一次采样精确预测三轮E2E差值。

后续若继续融合，应先减少value分片的重复准备、保留原求逆累加顺序并降低packet同步成本。两条kernel若更快就应保留；减少launch数或私有global字节本身不构成优化成功。

### 无损：已定位组件差异，不能用数值合格替代语义验收

新增诊断直接使用公开BF16 Q/K/V、FP32 gate/beta/初态，在T257/513/1024/4097、普通/弱衰减/近共线/零beta共16组上，分别运行公开融合和准备路线。**两条路线都独立对原FP64全历史oracle验收，原误差上限不变**；路线间比较只用于诊断。每组重复融合，输出及状态均稳定。

| 控制臂 | 与准备路线逐bit一致 | 输出差异相对L2最大值 | 状态差异相对L2最大值 |
| --- | ---: | ---: | ---: |
| 当前分块FP32求逆 | 4/16（均为零beta） | 0.03579% | 0.03085% |
| 仅恢复原FP32逐行求逆顺序，融合结构不变 | 16/16 | 0 | 0 |

分块臂最坏约0.525%的BF16输出元素改变；这是元素bit差异比例，不是答案错误率。对独立FP64，融合输出总体相对L2最大0.43855%、状态0.33162%；准备路线分别0.43855%、0.33158%。逐head的原验收也通过，不能把总体误差拿来替代逐head标准。

分块代入与逐行求逆在实数运算下求解同一个单位下三角矩阵：`[[A,0],[B,C]]`的逆下左块为`-C⁻¹BA⁻¹`。但FP32中改变乘加结合次序会改变舍入；后续BF16状态读出可能放大到少量元素不同。这次受控实验排除了“融合本身必须丢失精度”的说法，并分离出求逆顺序这一组件差异来源。它不证明所有可能输入都逐bit一致，也不证明语义质量没有退化。

完整模型进一步对照，输入均48,061token、单路、同seed、temperature=0，FP8/KVMem/vision相同，共16条完成请求：

| 执行条件 | 分块求逆融合相对B0 | 原求逆宽tile融合相对B0 | 各臂自身重复 |
| --- | --- | --- | --- |
| none、缓存OFF、上限128，各两条冷请求 | 128token全部一致 | 128token全部一致 | 全部一致 |
| none、隐式缓存ON、上限256，冷/热各一次 | 从第47token分歧 | 未补测此组合 | 冷/热一致 |
| DFlash2 K7、隐式缓存ON、上限256，冷/热各一次 | 从第6token分歧 | 256token全部一致 | 冷/热一致 |

所有冷请求cache hit=0，热请求hit=48,052、仅9个新token。分块臂的分歧在冷输入就发生，热恢复没有制造新分叉，因此本复现不支持“仅前缀恢复错位”的解释。普通贪心256token也分歧，**不是DFlash2独有的问题**。128/OFF与256/ON同时改变了输出预算和缓存策略，不能单凭两组差异断言缓存开关是触发原因。

恢复原求逆的模型候选与分块候选，CUDA源码文件SHA全部相同，冻结patch只有`prepare.cuh`的求逆计算/其scratch改变；同融合结构的组件控制则仅选择原逐行算法。两层证据共同支持求逆顺序改变为本次新增数值/生成差异的来源。

原构筑B0在相同缓存ON/256预算下，none和DFlash2也从第47token产生不同输出，保留该不利发现。源码的temperature≤0接受路线取target argmax及其首次不匹配处的校正token；不能用采样随机数解释此次贪心分歧。未采集首分歧处逐层状态、target logits margin、草稿排序与同选页集合，因此没有将分歧再断言为某个argmax近分、草稿或KVMem选页的独占原因。

结论：当前分块求逆候选**没有逐bit/逐token无损性**，却仍满足已声明的组件FP64标准；这两点不冲突。原求逆候选给出了在已测组件和DFlash2场景恢复一致的方向，但不证明所有工作量都精确相同。没有做语义裁判或正式多轮答案质量评测，不把token不同等同于错误率下降，也不宣称近似无损质量已验收。

GDN诊断测试已提交 `d2eb6fa5`（单独实验）及 `01cdfcc5`（组合实验）。命令为相应分支的 `ninfer_gated_delta_net_test --diagnose-routes`。原顺序控制只作为冻结诊断臂，已撤回源码临时改动；日常仍无GDN融合。

### HiCache隔离状态与“完整”的边界

- Native+KVMem基线：`codex/upstream-kvmem-native-20261008`，`6af5de4e`；当前NV分支基于它。当前源码没有`FileKVBacking`实现、HiCache配置及分层缓存测试。
- 可选增强：独立分支`codex/upstream-kvmem-hicache-optional-20261008`，`0a306396`，独立工作树`wt-upstream-kvmem-hicache-optional-20261008`；比Native多40个文件的变更，约3279行新增、183行删除。安装二进制也独立位于`runtime/upstream-hicache`。
- 默认关闭；参数`--kv-file-dir`启用文件层，`--hicache-ram-mib/--hicache-state-mib`配置热层与状态RAM配额，预取/write-through另行选择。当前日常运行`runtime/upstream-native`，不只是“包含HiCache但不开开关”。
- 已有单实例RAM/临时磁盘KV、校验、预取与生命周期功能；完整GDN/conv/DFlash StateImage仍在RAM，进程正常退休删除文件。没有重启恢复或跨实例完整检查点共享。
- 实验性能仍有负收益：前次容量压力回访66.22s/29.17s，相对Native12.63s/12.03s；预取ON11.278s、OFF10.069s。保留这些原声明条件的记录，未把功能测试通过写成Prefill提速通过。

“完整HiCache已完成”是过度概括。正确状态是**独立、可选的单实例分层KV实验，功能已有，完整持久状态与跨实例共享未实现，性能收益未验收**。继续保持与日常Native+KVMem隔离。
