# 动态 NVFP4 调度与批次宽度舍入诊断

**尾块算子有收益，完整长Prefill尚无已验证提速。** 1025～1536宽度的动态tile通过独立算子与有限模型状态验证，T1152两种实际K约快7～9%；默认1024块与双路合计2048没有改变路线。

残差舍入修改保留在独立数值实验分支，跨lane打包默认OFF：合法chunk128下出现两道可重复的数学长思考截断反例，阻止晋升；默认1024补测没有新增分叉，但不能擦除反例。关闭打包不能撤销该实验分支中的舍入修改。新48K工作集的None和DFlash2完整ABBA均已完成，各52批功能通过、22组请求四臂token一致；长双路TTFT分别变化+0.87%和−0.36%，没有可确认的长Prefill提速。HiCache与非CP GDN融合仍OFF。

本轮的根因证据已超过“误差可能累积”：CPU独立存储权重对照中，99.85～100%的第0层Q/K/V变动吻合FP32直接卷积与先BF16舍入的差别，后续NVFP4 A4继续放大差异。实际DFlash候选诊断进一步区分了草稿选路不匹配与验证数值分叉；34个条件位置中有1个已接受token不同于ordinary，固定NV投影A16能恢复ordinary选择，却让同一草稿本轮接受数从7降到4。Huihui和原版权重各84个实际selector选择均与独立FP64计算相同，两者都出现条件选路拒绝；不能仅归因Huihui或称selector算错。**接受率提高与输出对齐不是同一目标**；该小样本不能量化日常拒绝率或整体答案质量。日常服务尚未替换。

**长Prefill的收益抵消点已定位，最终硬件原因还在调查。** 实际48K双路的逐kernel跟踪中，NVFP4 gate/up约少59ms，down却多98ms，down激活量化多12ms。Attention/GDN仍逐路执行，耗时基本不变。旧粗粒度分析还漏算了打包路径，现已补齐外层Prefill标记；不能把漏算当成提速。下面保留实际时间线、连续算子实验与社区证据，区分观测结果与缓存假设。

## 动态调度的收益和适用范围

原来 256-token tile 在 1025～1536 的部分输入上有填充计算。128-token tile、三阶段流水线能减少这部分成本，但对 1024、2048、4096 等整块会降低复用、增加执行成本。因此只在 1025～1536 使用它，保留所有其他区间。量化尺度布局和计算 tile 由同一个条件选择。

公共 Op、冷 CUDA event、8 次预热/30 次重复，ABBA 两个观测/臂；两种实际残差形状 N=5120，K=6144/17408，覆盖 T=1～128 每个整数及 192～4097 的关键路由边界。用户应用保留、时钟未锁；下列是组件耗时，不能换算成相同比例的整机收益。

| Token 宽度 | K6144 耗时变化 | K17408 耗时变化 |
|---|---:|---:|
| 1024 | −0.07% | +0.04% |
| 1025 | −3.89% | −6.26% |
| 1152 | −8.59% | −7.35% |
| 1280 | −7.25% | −6.40% |
| 1536 | −3.35% | −1.93% |
| 2048 | −0.18% | −0.14% |
| 4096 | +0.28% | −0.55% |

未改动的整块小幅变化归入本轮观测波动，不记优化收益。全面改成 128/2/2 的 T1024 曾退化 17.94%/24.92%；128/3/1 全面替换也退化，1537/1664/2048 边界尤其明显，原失败和负收益没有删除。独立 seam 测试覆盖 1025、1088、1152、1216、1280、1281、1344、1408、1472、1535、1536、1537。

### 为什么是尾块收益

T1152/K17408 的 NCU 对照确认原路线 200 CTA、1.18 wave、384 线程、168 寄存器、85120 byte dynamic shared；新路线 360 CTA、2.12 wave、288 线程、143 寄存器、56448 byte dynamic shared。两者 active warp 均约 18.6%，收益没有来自更高 occupancy。256-token tile 要填到1280，128-token tile 刚好1152，减少10%的填充宽度；Tensor 的 SM 间活跃差异也收窄，符合少空算、改善尾部均衡的解释。不能将它断言成唯一成本：tile 同时改变复用、producer、网格和资源使用。

NCU Tensor 平均活跃51.94%→52.47%，DRAM10.55%→13.11%；17遍计数器重放、未锁时钟/缓存，这些只用于归因，不参与性能计分。[NVIDIA GEMM指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)解释 tile 复用与填充/末 wave 的取舍；[FlashInfer b12x](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/gemm/kernels/dense_blockscaled_gemm_sm120_b12x.py)也按形状选择 tile，不能简单全面换小块。

### 数值和模型状态验证

82 个算子调用通过独立存储权重 FP64 oracle，保留原容差，检查输入/权重不变、workspace 报价、边界保护及 Graph replay。历史76个完整 BF16 输出合计311920640 byte与旧256-tile基线逐字节一致；新增1281/1535/1537的6项只有独立oracle，未伪称拥有旧输出。

同一新二进制的普通/打包模型回归分别通过 None 138.42秒、DFlash2 K7 162.11秒：128/256/384/512/640/768/896/1024/2048 九种实际块、不同最终长度、重复基线；GDN、卷积、tail、Main KV/scale、投机后端状态以及贪心 Begin 输出精确一致，资源最终归还。特别覆盖640+640=1280、768+768=1536进入新路线、普通单路仍用256tile的情况。这是有限夹具证据，不是所有输入严格无损证明；不覆盖Vision、缓存生命周期、36K换页取消和完整两路256K峰值。

48K长请求主要用1024块，双路合并为2048，均保留原路线；尾块组件有收益并不意味着它能解决此前长Prefill没有提速。完整新角色夹具的E2E仍需同配置测量，旧全System夹具结果不能混用。

## 原有舍入缺陷：现在有本机因果证据

社区 [NInfer #374](https://github.com/Neroued/ninfer/issues/374)指出 `FullTokens` 可能让编译器把累加器乘尺度、加残差收缩为FMA，尾块则两次舍入。我们独立构造了两项可精确表示的点积、非二进制整幂的尺度和近抵消BF16残差，并将完全相同的输入/残差重复到每列；没有调用GPU实现生成CPU参考。

两种实际K分别测试66/75个宽度。T32/64/96/128/192/256/384/512每列均有155行不同于尾块；这155行全部逐bit匹配CPU单次FMA预测，尾块全部匹配先乘后加预测；所有列内部一致。独立数学oracle仍全部通过。这说明原容差与普通随机输入能漏掉宽度相关舍入，不能只用“数值误差达标”证明缓存或打包状态等价。

当前TMA（513～2048，包括新尾块）在此夹具均匹配先乘后加；本轮局部调度没有新增该差异。但普通/打包小块跨route可能改变舍入，之前用实际模型得到差异的具体层/权重尚未逐层复现，因此不能将所有旧状态差异都归为这一个原因；FP8 Split-K的求和顺序问题独立存在。

### 修复和旧输出的实际差异

独立实验 `codex/nvfp4-residual-rounding-20261010` 为 NVFP4 A4 残差 epilogue 明确使用 `__fmul_rn`、`__fadd_rn`，保留原长 TMA 两次舍入。只有该残差消费者要求明确舍入，普通投影、其他融合消费者、A16 decode 和 FP8 路线保持原合同。没有全面禁止编译器 FMA，也没有把 FP8 的求和问题当成同一个修复。

本机代表性 K6144、M32/N64 `FullTokens` 的 SASS 从 8 条 FFMA 变成 8 条 FMUL 和 8 条 FADD；tail 原来和修复后都是两次舍入。29 个 NVFP4 A16 residual kernel 的完整指令及编码 hash 与修复前一致。编译器实际输出与 CPU 单次/两次舍入预测相互吻合，已形成源码、SASS、GPU 输出三层因果证据。

| 核对项 | 本机结果 | 能说明什么 |
|---|---|---|
| 近抵消宽度回归 | 两个 K 共141项，宽度/列/既有长块舍入差异均0；独立 FP64 oracle 全通过；Graph 32/512/1280重复通过 | 修复该夹具中的批次宽度依赖 |
| 常规独立算子 oracle | 82项通过，原容差保留 | 没有用放宽容差掩盖差异 |
| 修复前后完整 BF16 输出 | 79/82逐字节一致；3项不同，严格旧输出断言失败并保留 | **修复不能标为严格旧输出无损** |
| 同一修复二进制普通/打包模型 | None 119.09秒、DFlash2 K7 130.95秒；九种块，状态和 Begin 输出精确一致，资源归还 | 有限模型夹具的打包一致性；不是旧/新质量对照 |
| 组件 ABBA | 149宽度×两个K，两次观测/臂，耗时变化中位数均0；未锁时钟 | 修复主要是正确性，不记作性能优化 |

3项不同均为 K6144 A4 的 T128/256/512：分别40/655360、120/1310720、120/2621440个 BF16 元素不同；最大绝对差0.00024414/0.00097656/0.00097656，relative L2 为7.60e−8/3.08e−7/2.23e−7。误差小不证明近似并列 logits 不会改变下一 token。常规 oracle 通过与严格旧输出失败是两个不同结果，都保留。

上述普通/打包模型回归只对实际块大于512启用打包；128/256/384/512项没有实际 packed batch，不能写成小块打包验收。

另一个实验分支 `codex/nvfp4-small-packed-20261010` 已将资格边界开放至256：在舍入修复的基础上，gate/up SwiGLU 普通路径须已经使用TMA，避免同时跨越尚未验收的另一条算术边界。新 None 112.64秒、DFlash2 K7 125.09秒的九块回归全部通过；256/384/512/640/768/896/1024/2048每项均实际执行2个packed batch，128明确回退为0。普通重复与打包的状态及贪心Begin token精确一致，最终资源归还。耗时仅为测试运行时间，不是速度A/B；尚未据此声明整个Prefill提速，也未覆盖Vision/缓存/稀疏页取消或所有输入。

旧r2/新修复服务分别测试代码、数学、文字各三题、短/约7.3K/12.1K输入，共27个条件，每臂每条件两轮。两lane配置但逐请求对照，4K窗口/16K逻辑上下文、2GiB pageable、None、Native OFF、pack OFF、Vision OFF、chunk128；它故意密集触发被修的旧small FullTokens路线，不能推广成默认1024块的分叉概率。r2之后其他有效差异为遥测、测试和1025～1536尾块选路，128块不进入尾块区间。

按SSE response ID关联Engine token数组，所有冷输入实际cache hit=0；各臂27/27自身两轮token完全一致，旧/新只有9/27完全一致（代码3/9、数学4/9、文字2/9）。首次不同可在第1～523个token。代码9/9每臂都通过独立函数用例，文字9/9每臂都保留四项事实，但150～200字的格式通过分别4/9和1/9。数学原1024预算分别截断5/9、3/9；这些不得当作完成答案或错误答案。原严格夹具分数17/27、16/27混合了截断与格式，不能据此报告质量下降百分比。

数学另用相同输入、2048预算重做9条件×两轮：旧/新token4/9一致，自身重复全一致；旧全部完成且算术答案正确，新有两项仍截断，其余7项完成且正确。有完成答案写`FINAL ANSWER:`而非规定`FINAL:`，原格式失败继续保留；另增保守的终末标签整数核对，不修改原判分。

两项截断又用相同4096预算各臂两次重做：旧版分别1487/1404 token完成且算术正确，修复版均4096 token后截断，自己两次完全一致；与2048运行的已生成token前缀也完全一致。首分叉分别第71/523个token。修复版正文出现正确整数但未给终末答案，不能算完成；末1024 token的16-gram最高仅重复2/3次，没有短字符串机械循环的证据，不能仅凭过长思考断言死循环。**这是可重复的负结果，阻止直接晋升日常。** 也不能将两题推成总体质量下降率。继续固定为回归反例，并用默认1024块补同输入对照；不靠继续扩大预算宣称问题消失。均未做语义裁判或正式多轮质量验收；期间有CPU编译，计时只保留用于排错，不记性能差异。

默认1024块的两题补测已经完成，仍各臂各两次、2048预算：两题旧/新token均完全一致，自己两轮也完全一致；其中一题两臂都完成且正确，另一题两臂都截断。因此没有在该对照中看到修复新增分叉，也不能写成两题均完成的质量通过。它支持影响与chunk128频繁进入被改aligned small route有关；不足以保证所有1024请求、尾块或缓存拆分单元都相同。用户要求覆盖全部负载，合法128配置的反例仍然保留。

结论是**修复解决已证的宽度舍入缺陷，同时确实会改变实际旧生成输出**，不能以“数学上同一个表达式”代替逐token一致，也不能把文本变化直接判成答题质量下降。继续留在独立实验分支。

### 社区理解，以及与本机方案的区别

[NInfer #374](https://github.com/Neroued/ninfer/issues/374)截至2026-10-10仍Open，未见维护者定论。报告者最初采用统一FMA，随后 [ValerioDolci 的修法](https://github.com/ValerioDolci/ninfer-tp2/commit/c3383145)按格式保留原长块行为：NVFP4乘后加、FP8 FMA；其质量数据属于fork作者报告，不能替代本机结果。

[Wallawalla47 的修复](https://github.com/Wallawalla47/ninfer-custom/commit/21ef82324871fee6c74a3623012b31731d25ac9e)同样固定NVFP4乘法舍入，但没有因此宣称FP8宽度问题完全解决。本机方案进一步只改NVFP4 A4残差消费者，避免顺带改变其他融合算子。这里借鉴的是因果机制，并非未经核对整体合并fork。

另一个整合fork [ninfer-all](https://github.com/iamwavecut/ninfer-all)提供按设备/宽度选路、SM wave对齐和其他缓存机制，却明确记录其Qwen27B/5090的8K～32K Prefill退化，以及批次与单请求近并列token分叉增多。将设备自动选路列为实验候选，不能把其他模型的收益当成当前NVFP4默认路线的收益。

### 另一个独立机制：激活精度随宽度变化

只修FMA不能得到跨所有宽度、后端的严格无损保证。当前artifact有168项`AllowA4` Use，实际MLP gate/up/down均允许A4；参数绑定忠实读取这个合同。NVFP4 down的K17408在T8开始选A4、K6144在T17开始选A4。投机验证使用的合并列数可能跨这个边界，不能仅看“权重仍是同一个NVFP4”便认定与T1 decode算术完全相同。

本机增加**诊断而非数学精度验收**：用真实目标第0/7/28/55层的K17408 down权重、每列完全相同的公开合成BF16输入，在T1/2/4/7/8/16/17/32比较允许路线与强制A16。T1～7同宽度两臂完全相同；T8及以上变成A4后，四层分别5013/5030/5035/5020个BF16元素不同（每层5120），relative L2为10.67%/10.30%/10.44%/9.82%。这说明算术profile差异明显大于本轮残差FMA的低位舍入差异，**不是这几层的独立FP64误差，更不是答案退化率**。

强制A16跨宽度仍有少量低位差异，例如第55层T8比T1不同4个元素、relative L2 2.35e−6；固定激活精度也不自动固定所有归约舍入。诊断43.59秒正常退休，未更改默认精度；合成输入不是实际prompt的隐状态，不能用它直接推定实际首分叉logits的原因。

[NInfer架构合同](https://github.com/Neroued/ninfer/blob/master/docs/maintainer/engine-architecture.md)允许合格算术路线按形状选择；[vLLM投机无损说明](https://docs.vllm.ai/en/latest/features/speculative_decoding/#lossless-guarantees-of-speculative-decoding)也区分算法无损与有限精度、batch差异。[vLLM Batch Invariance](https://docs.vllm.ai/en/latest/features/batch_invariance/)通过固定归约与执行约束改善一致性，并明确存在性能取舍。它不是当前NInfer/Qwen27B NVFP4已完成一致性证明。

固定前缀逐层诊断已经完成。实际Frontend的代码/数学/文字三类任务，短输入/加128段公开archive共六个前缀；相同token、位置、Main KV和GDN源状态，比较真实ordinary W1和RecordForReplay W8，B1/2，以及原精度/NVFP4投影A16/所有可指定投影A16。记录embedding、64层mixer及MLP后的第一因果列、logits与top1/top2。W1操作独立复制的GDN状态，W8记录到Replay区；每个病例确认原GDN源逐byte不变、句柄和物理资源全部归还。诊断62.61秒结束，最低commit余量16.78GiB、物理内存27.25GiB、显存4986MiB。没有在普通服务路径增加trace分配、复制或同步。

实际第0层GDN投影是`FP8_E4M3FN_ROW_BF16`、AllowA8、[16384,5120]，不是NVFP4投影。源码的FP8 snapshot resolver在B1/W≤3选择FusedA16；W8或B2的本组列数≤16选择MaterializedA16，**17列才跨A8边界**。所以本组第0层首差异不能归因于FP8 A8激活量化。公开接口注释原写T8边界，与实际实现不符，已按实现改为T17，不改变运行行为。

`GdnConvEpilogue`直接以FP32投影累加器进入卷积FMA，然后将投影写成BF16历史；materialized路线先把当前投影落成BF16，再读回进入同一卷积表达式。这是已核对的实际舍入边界差异。两路投影的GEMV schedule和归约次序也不同。因此**证据已把问题定位到投影/卷积执行路径，尚未通过相同累加器的控制实验分别量化“BF16中间舍入”和“点积求和次序”的贡献**；不能把二者合写成已证实的单一卷积bug。

进一步核对[官方机制说明](https://inco.ai/blog/dflash2/)及[参考实现](https://github.com/z-lab/dflash/blob/main/dflash/model.py)：selector使用 `S_t(a,b)=U_t(b)+dot(A(a)*H(h_t),B(b))`，并从实际前驱逐位置选择；它不是只取unary第一名，也不是全局Viterbi最优路径。因此目标在top16而没被选中，只能先归为条件选路/分布不匹配，不能当成selector代码错误。本机候选算子的FP64 lattice oracle已经覆盖相同公式，随后补采了实际unary、projected hidden和前驱/候选codebook，结果见下面的新诊断。官方所说suffix decay是**同一个草稿块内的位置**，不是总上下文越长接受越低的证明；总上下文效应还需固定任务、前缀、采样及目标权重做成对对照。

[SGLang #39254](https://github.com/sgl-project/sglang/pull/39254)提出另一个工程根因：compressed-tensors草稿的packed `fc`数据在普通Linear加载器中被静默跳过，层保持随机初始化；作者及另一用户报告修复后接受恢复。截至核对时PR仍Open，不写成已合并或维护者确认。NInfer对应的是 `feature_projection`：`bind_draft`必须声明参数，Binder在binding缺失/形状不匹配时抛错，Materializer检查完整上传，没有这条静默随机初始化路径。这排除了**同一已描述机制**，不证明本机草稿转换或权重内容全部正确，也不支持直接移植SGLang的Python加载器。原版/Huihui及原始草稿权重的进一步对照仍要保留。

### 长 Prefill 打包为什么没有明显收益：矩阵成本上限

当前打包只合并NVFP4 FFN，attention/GDN仍逐路运行，8个FP8 FFN保持各自归约顺序。两份输入仍需两份数学运算；合并主要省重复权重读、launch和小矩阵低效率。实际1024块已经较大，不能从decode的双路近翻倍推导Prefill同等收益。

用已有公共NVFP4 SwiGLU `[34816,5120]` benchmark，对1024/2048/2048/1024各做8预热、30冷CUDA-event采样，保留应用且不锁时钟：两次1024的中位耗时均值为599.552µs，一次2048为567.600µs，合并组件成本低5.33%。既有四臂down `[5120,17408]` 数据中，一次2048比两次1024仅低0.30～1.11%；另一个K6144形状约低4.01～4.47%，不能拿较好形状替代模型实际FFN down。

连续调用同一公共SwiGLU再调用down的补充实验，保留两者之间的实际producer/consumer缓存状态：两次1024中位耗时均值900.736µs，一次2048为868.128µs，组件对成本低3.62%。与独立SwiGLU的5.33%是不同实验，不把差额当成精确的down回退。synthetic存储权重、残差及相同stream下仍有少量收益；尚未复现整模型down回退，说明仅用孤立算子结果不能解释整模型。

随后只加载实际v3目标artifact第4层的两个NVFP4 FFN parent，经正常Binder/Materializer保持原始布局、尺度和激活divisor，输入/残差仍为synthetic：ABBA两次1024均值900.224µs，一次2048为866.992µs，成本低3.69%，与synthetic权重结果接近。这排除了“只有合成权重才有此组件收益”的解释，仍不能代替真实激活、其他层权重和整个模型的缓存/执行环境。bench功能已独立提交，未改变生产算术。

整请求Nsight OFF/ON已经采集：两路各48057实际Prefill token，ON实际44批/90112 packed token；两臂输出逐token一致。CUDA launch与最内层NVTX类别关联后，各kernel只计一次：

|---|---:|---:|
| Attention及其投影 | 3.7088s | 3.7231s |
| GDN及其投影 | 2.3744s | 2.3795s |
| FFN/post-mixer | 3.2143s | 3.2652s |

FFN内部，NVFP4 fused SwiGLU由5488次/1.61361s降至3024次/1.55442s；实际K17408 down由5152次/0.73493s变成2688次/0.83319s，down激活量化约0.05319→0.06506s。多出来的down与量化成本抵消gate/up节省，解释本轮为何整体没有收益，但仍需区分具体缓存、访存和执行调度原因。H2D量与时间约740.22MB/0.1004s、D2H约1576.11MB/0.2047s，两臂近乎相同；源码中residual从起点即连续，MLP前没有新增逐lane gather，不能将结果归成新增复制太贵。

旧分析以外层 `prefill` range定位工作，普通路径有此标记，打包路径只有 `prefill.chunk` 等内层标记，导致ON只统计约0.771s而OFF约9.301s。所有CUDA事件实际都在trace中，绝非90%提速。现已给 `run_prefill_batch`补同一外层range，构建与scheduler/request-log两项测试通过；旧数字保留并明确标记为不完整范围。新标记不改变GPU算术，也不等同于HTTP面板的JSONL采集。

社区与当前代码的核对：[NInfer #263](https://github.com/Neroued/ninfer/issues/263)讨论ragged SwiGLU减少中间物化，但本机已对T≥256走融合TMA，1024/2048本来就融合，不能再记成此轮长Prefill新增收益。[#277](https://github.com/Neroued/ninfer/issues/277)作者在2332-token单请求上通过增大chunk减少同步、得到有限改善，单个首token一致不证明所有chunk输出数学中立。[#303](https://github.com/Neroued/ninfer/issues/303)的多块执行仍是作者明确未完成验证的提案；在KVMem下必须保留逐物理子块滚动、页许可与取消边界，不能照搬成一个大事务。这些均不是维护者已经确认适用于本机构筑的速度结论。

## 实际 selector 分数：实现正确与预测正确是两件事

为免工作区复用覆盖证据，native探针在真实selector之后将实际unary、256维BF16 hidden及anchor复制到独立缓冲；同步后只收集真实前驱及top16候选的codebook列。默认服务不设置这三个缓冲，没有新增复制/分配/同步。运行方法见 [native诊断说明](native-diagnostics-20261010.md)。

独立FP64计算逐候选条件分数，保留FP32舍入误差上界；不是调用GPU算子生成oracle。候选算子独立测试通过后，Huihui与原版权重各6个公开前缀、两路、7个草稿位置，共168个实际选择均恰好等于CPU条件argmax。Huihui开启探针前后30份候选、q、草稿、目标及目标logits文件逐byte相同，验证采集没有改变本组实际数学输出。

Huihui四个**首拒绝**处，以下差额都为“所选候选减目标候选”：

| 前缀 | unary差额 | 条件项差额 | 合计 | 原因 |
|---|---:|---:|---:|---|
| 代码/短，位置3 | −1.1001 | +1.2361 | +0.1360 | unary原本偏向目标，条件项翻转排名；目标端两token logits相等，但greedy按确定规则选择另一个 |
| 数学/archive128，位置6 | +0.7300 | +0.1744 | +0.9044 | 草稿unary与条件项都偏向错误候选 |
| 文字/短，位置4 | +2.3645 | +0.7338 | +3.0983 | 同上，目标在候选第16名，召回有而打分不匹配 |

原版权重也有五个首拒绝、目标均在top16。代码/短同样被条件项翻转排名：unary差−1.0097、条件差+1.5326、合计+0.5229；文字/短与archive128则条件项在缩小unary错误但不足以改选。原版六前缀每路接受数为3/5/7/0/3/0，Huihui为3/7/7/6/4/3。**两模型自己生成的32-token teacher轨迹并未强制相同，不能用18对30宣称Huihui更好或更差。** 两者出现相同机制，已否定“仅Huihui才会发生”的解释；还没测出Huihui对日常接受率的净因果贡献。

原版权重的23个ordinary条件反事实位置中也有一例已接受token分叉：代码/archive128位置4，verify/草稿选4087，ordinary选61446，此前位置一致。固定NV投影A16或所有指定投影A16均恢复61446，让同一草稿接受从5降到4。Huihui对应例也能通过NV-A16恢复ordinary。这说明验证精度/宽度路线问题同样存在于原版权重；不是只在消融后才有。1/23或1/34不作为总体分叉率，不将未访问的后续位置归入拒绝。

同时核对了计时源码：`PrefillState.elapsed_seconds`对每个参与packed batch的请求记录共同经历的整批时间，因此per-request `timings_seconds.prefill`不可相加作GPU成本；顺序执行的两个请求则各自只累积自己执行段。此口径能让打包前约5.1秒/路变为打包后约9.4秒/路，**不能由此推导Prefill算力耗时翻倍**。`first_output_timing.prefill`的submit/wait/post/gpu成本按token数分摊，最后一行吃余数；native回归已断言各行之和精确等于整批。因此没有在可相加的工作账本中重复计算。

对照结论使用整批实算token/墙钟、末路TTFT及完整GPU时间线。夹具中的`maximum_chunk_gap_seconds`是SSE内容事件间隔，不是物理Prefill chunk耗时；长C2 ON观察到约0.16秒、OFF约0.05秒的事件间隔，而引擎decode执行段仍约0.034～0.040秒、实际提议与接受数相同。仍需调度时间线才能将事件间隔的变化归因到peer Prefill等待，不能将其直接写成decode内核退化3倍。

## 原始 DSH 请求与保护阈值续测

## 单遍计数器：实际模型 down 继续归因

这次使用安装中的舍入实验之前r2，不使用后来编译的Op bench数学来替代真实模型。实际公开48K×2输入，None、FP8、Vision、Host4GiB pageable、NativeOFF，chunk1024；选全局NV down ordinal1120（第0层）。每设置/计数器组只采一个真实kernel，保留原前序计算与实际activation/workspace；OFF/ON实际grid为40×4/40×8，block均384线程，ON整请求期间实际打包92160token。两个请求都完成，各输出5token。这里的计算前沿随调度/宽批不同，时钟不锁、没有工具cache flush，不能当相同前序状态的严格因果实验或无profiling吞吐成绩。
