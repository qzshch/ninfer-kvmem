# DSH 长上下文与跨请求 Prefill：验证记录

本轮目标是修复真实 DSH 请求的容量拒绝与双路等待，使代理显示实际执行槽数，并验证跨请求 NVFP4 投影打包。每路仍是 262144 逻辑上下文、576 页（36864 token）工作窗口，FP8 KV、DFlash2 K7、Vision。不能通过缩短输出预算获得“并发成功”。HiCache 和实验 GDN 融合保持关闭。

工具异常已有可复现的长历史案例及有效修复。滚动窗口以前只固定保留最前面 128 token，系统指令和工具定义其余部分可能被淘汰。现在 Frontend 标出真实指令范围，KVMem 在 prefill、replay、decode 和缓存恢复时优先保留它们；本次实际指令占 153 页，日志核对全部保留。用户文本里的伪造标记不会变成指令。

## 验收方法

- 容量：原始数学、Jev 请求原样并发重放；用取消限制测试时间，不修改 max_tokens。检查实际两 lane 同时推进，取消后资源归还。再测试大于旧 Host 容量的历史输入及边界增长。
- 工具：保留原始 SSE 和生成文本；分别核对结构化调用、参数和异常闭合。测试不执行模型产生的命令。不能把拒绝解析错误 XML 当作修复了生成。
- 打包：默认关闭，普通执行为对照。先验证独立 lane 的 GDN/conv、KV、continuation hidden、草稿状态和 greedy Begin；再覆盖页交换、缓存、取消、Vision 回退和混合 decode。无状态投影可以合并，attention/GDN 的身份与状态不能串 lane。
- 性能：同一个二进制开关 A/B，短输入、48K 长输入、不同块大小及混合请求；报告 Prefill 总吞吐、TTFT、decode 最大暂停和有效打包次数。至少交错重复，保留负结果。
- 安全：保留用户应用和内核编译；运行期 Windows commit 余量至少 12 GiB、物理内存至少 8 GiB、GPU 余量至少 768 MiB、无显著 swap 增长。触线仅停止测试模型。

## 已确认的事故原因

我们此前临时恢复服务的命令重复指定 Host 容量，最后的 `--host-context-mib 4096` 覆盖前面的 8192。这是我们配置的问题，不能归咎用户。工作窗口限制的是 GPU 驻留历史，不是完整 Host 历史。全 256K 输出预算还会参与未来容量准入；两个这样的请求不能在 4 GiB 池中得到同时驻留资格。

两条实际请求已经立即通过 NAS 代理转发。后到请求在引擎中排队约 623 秒，直到前一个数学请求结束。因此，代理槽数 3 不是这次串行的根因。后续数学会话把约 149K token 历史重新提交，超过旧 Host 池的孤立输入容量。

代理已增加自动 lane 发现、真实 queueWaitMs/upstreamMs、流内错误记录及按时间保留最新请求归档。引擎 API 已提供 max_concurrency。异常工具生成增加了字节拆分解析回归；未证明生成异常已修复。

## 内存试验

6 GiB 锁页 Host 池启动测试在 Windows commit 余量约 10.36 GiB 时被保护停止，未出现 OOM。GPU 余量约 947 MiB。此结果不支持直接扩大至 18 GiB 锁页池。小型分配探针受到系统波动影响，不能据此声称确定的每 GiB commit 成本。

新增显式 `--host-context-memory pageable` 实验模式：固定容量和全部所有权、准入、字节表示不变，普通内存替代整池锁页。默认仍为 pinned。CUDA 的普通内存异步搬运可能阻塞 Host，必须验证复制完整性、生命周期、实际内存峰值和 E2E 成本后再决定日常使用。容量字段表示分配地址容量，不能当作普通内存的实际 RSS。

## 实验状态

跨 lane 打包目前合并 NVFP4 dense FFN 投影，attention/GDN 保持逐 lane 执行；最终采样、视觉输入、MTP、capture/rewrite 和稀疏查询回放边界回退普通路径。DFlash 的每行 CPU ingress 独立分配，避免异步上传未结束时被下一行覆盖。

重复未打包基线完全一致。最初将后段 FP8 FFN 合并后，1024-token 块出现状态差异：FP8 的 bulk Split-K 选择依赖总宽度，合并前后 FP32 求和关联顺序改变。现在 FP8 保持逐 lane 执行。另一个384-token案例聚合后跨越NVFP4 cp.async/TMA路由边界，也出现差异；现在仅普通路径已使用TMA的>512-token块可打包。两项失败和不合法的小块测试记录均保留，不用宽松容差抹平。

None 和 DFlash2 K7 已测试128、256、384、512、640、768、896、1024、2048九种块大小，每路输入分别为3块和3块+17 token。较小块回退，较大块实际打包。两者的 GDN/conv/tail/greedy Begin，以及有效Main KV字节和量化尺度逐字节一致；DFlash2还比较了Backend KV及完整草稿状态。None完整状态补测114.69秒通过，DFlash2 K7 137.89秒通过。分页、缓存、取消、视觉与混合decode，以及E2E性能对照仍在进行；目前不能声称吞吐收益或完整无损验收。

18 GiB pageable配置保留原数学/Jev请求输出上限238874/238904，重放记录到6个两路实际decode区间，没有流内错误。但长历史和两路满256K峰值还不能据此判定已通过。

追加完整长历史重放：原数学会话132940生成token的完整记录作为assistant内容构成派生夹具，实际149879输入token全部计算，输出1133；另一条原数学输入16917全部计算，输出1816。两者保留238874输出上限，用客户端取消限制运行时长，记录9个实际双路decode区间；约1.17秒后两级代理及Engine退休。该夹具不是已经遗失的第二轮原HTTP正文，也不是答案质量验收。

该模型稍后达到Windows commit保护线：余量10.42GiB，物理25.65GiB、GPU1687MiB、WSL约27.89GiB可用、swap0。只停止测试模型，未发生OOM；两路满256K仍未测试通过。不能因为Linux空闲或pageable启动成功就宣称整机容量安全。模型停止前后的现场采样显示commit释放约35GiB，不把这一整体差值全部归因Host池。用户应用、自定义内核、镜像网络和36GB/8GB WSL配置均保留。

服务端打包开启的短/长冷输入完成四组；两路实际各48061 token冷输入均结束。后续混合组在缓存累积后再次达到12GiB commit保护线，最终SSE连接被中断，整轮保持失败状态。停止前Host记录occupied约5.15GiB、KV4.14GiB、五个Host状态；这些仍有所有权，不能据此断言泄漏。后续将关闭跨请求缓存的计算A/B与开启缓存的生命周期/回访验证分开，保留本轮失败，不将降配结果混入同配置成绩。

测试工具两项失败也保留：长历史runner首次误把SSE空role事件当首token，尚未完成Prefill即取消；服务端runner首次误把Engine的stop_token当作协议stop而拒绝。修正夹具后使用新证据目录重跑，未覆盖原失败。cache mode explicit只关闭隐式写入提示，不能保证已发布前缀不会读取；冷对照必须核对实际hit=0。

GDN 融合在本机此前 T256～4096 的组件测试中没有确认正收益，且改变了部分表示状态。继续默认关闭。要成为正收益，省下的搬运/启动成本必须超过重复准备和同步成本；目前没有已验证的正收益配置。

## 追加：36K 边界取消与动态 NVFP4 调度

非投机路径的跨 lane 打包边界取消已通过三次：取消目标实际计算 40960、43008、39936 token，均超过 36864 工作窗口；实际打包 26624、26624、31744 token，记录 6、6、7 个双路 Prefill 区间以及 48、80、32 个 demotion 页。幸存路各 48046 输入 token，输出与独立完整执行精确一致，最后 Engine 归零。取消到两路均退休为 4.274、4.386、3.156 秒，包含幸存路继续完成的时间，不能解释为取消目标延迟。配置为 6GiB pageable、Native OFF、两路 256K 逻辑上限、36K 工作窗口、Vision 启用，但该夹具没有图片；不替代 DFlash2、缓存、视觉或完整容量验收。之前身份关联错误和 commit 保护停止的两项失败仍保留。

动态 NVFP4 的第一项新候选将残差投影的大块路径从 256-token tile/三阶段/每 SM 至少一 CTA 改为 128-token tile/两阶段/至少两 CTA。两种实际形状 N5120/K6144、N5120/K17408 分别通过独立 FP64 数学 oracle（直接解码存储权重与尺度，保持既有容差）；76 个完整 BF16 输出与基线逐字节一致，覆盖热小块、512/513/1023/1024/1025 及 1536/2048/4096。此有限夹具不等于所有输入严格无损。首次导出因重复调用使用同名文件而拒绝覆盖，保留失败；修正唯一 case 序号后重新构建两个臂，未覆盖旧证据。

性能采用公共 Op、冷 CUDA event、8 次预热/30 次重复、ABBA 各两次观测；覆盖两种 K、T=1～128 全整数和 192～4097 的路由/块边界，用户应用保留、GPU 时钟不锁。这不是 E2E 吞吐。候选大多退化：T1024 的 K6144 耗时 69.040→81.424µs（+17.94%），K17408 156.752→195.808µs（+24.92%）；T4096 分别 +18.29%/+24.70%。1152 等个别宽度有小幅降低，不足以支持全面启用。候选不晋升日常构筑。

同一 T1024/K17408 的 NCU 对照中，128-token 两阶段候选的 Tensor 活跃率 65.85%（基线 78.09%），DRAM 活跃率 22.91%（34.79%），活跃 warp 占比 33.60%（18.61%）；每 issue 的 short-scoreboard 等待 1.897（0.066），long-scoreboard 1.767（0.879）。更高 occupancy 没有改善 Tensor 执行，较短流水线与较小 tile 增加等待、降低复用；需要三阶段独立对照来分离影响，不能断言其中某项是唯一原因。derived local/shared spilling requests 均为零。计数器多遍重放、未锁时钟和缓存，采样耗时不参与性能评分。

当前另建 codex/nvfp4-dynamic-projections-20261010 实验分支继续三阶段对照。跨请求打包、HiCache 和非 CP GDN 融合仍默认关闭；完整两路 256K 物理容量、DFlash2 跨窗口取消、角色修正后的 E2E ABBA 尚未通过。没有降低既定安全线，没有重置 WSL 或停止用户内核编译。


## 根因与社区理解（2026-10-10 核对）

| 问题 | 本机构筑中已确认的机制 | 社区资料与适配边界 |
|---|---|---|
| 长历史容量拒绝、双路等待 | GPU 36K 工作窗口只限制驻留集合；全历史、后端历史和恢复 state 要用 Host。我们的恢复命令误把 Host 设为4GiB；未来输出准入额度使后到请求等待。18GiB保持原输出预算后已观察真双路，但完整物理峰值仍受整机commit限制。 | [NInfer资源合同](https://github.com/Neroued/ninfer/blob/master/docs/maintainer/resource-scheduling-and-context-cache.md)区分逻辑长度、物理池、预留和抢占。[#386](https://github.com/Neroued/ninfer/issues/386)是另一位用户的新缓存压力失败报告；其关于输出上限的因果是作者猜测，不是维护者结论，且日志max_concurrency=1，不能据此声称双lane缺陷与我们相同。 |
| 36K内工具生成异常 | 旧sink只保留128token，而工具定义/系统指令约9.8K。指令页离窗后，仅靠相似度检索不能保证模型仍看到工具schema。扩大驻留窗口或保留真实指令范围都消除本次复现；不是只有解析器，也不能仅归因DFlash2。 | KVMem-qw3当前main `1cf3b2f` 的[server](https://github.com/kvmem/kvmem-qw3/blob/1cf3b2f/src/qw3_server.cpp)和[mandatory fitter](https://github.com/kvmem/kvmem-qw3/blob/1cf3b2f/src/kvmem_request_plan.hpp)按SystemControl/CurrentQuery等语义范围保留块。它在超预算时可缩减范围、让部分内容参与检索；我们对完整指令自身超窗显式拒绝，不能把两种超预算语义说成相同。 |
| sparse Vision冷热差异 | 物理子块/typed rewrite会改变选页。热Prefill在同一permit执行第二块时没有重新滚动，读到冷replay已淘汰的103页，造成真实因果上下文不同。每物理子块返回调度重新报价/滚动后，None/DF2/MTP冷热与恢复回归通过。 | [#303](https://github.com/Neroued/ninfer/issues/303)讨论有界多chunk减少同步，作者明确尚未完成验证。这是性能方向，不能越过KVMem选页/许可边界；若重新合并单元，必须逐子块滚动和持有合法资源。 |
| NVFP4大块没随双路加倍 | 长块已经能较好利用Tensor；两个请求增加的是计算量。打包减少启动/重复读权重，只在这些成本重要时有益，不会减少两份模型数学工作。原48K日志没有执行513～1023的已优化区间，长请求无收益有直接路线证据。 | [vLLM V1调优](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill)把Prefill视为偏计算、decode视为偏带宽，并用混合batch改善利用率；这是典型规律，不能替代我们的分阶段计数器。当前NInfer打包仅FFN投影，attention/GDN仍分路，不能等同vLLM完整混合计算batch。 |
| 小tile/高occupancy候选变慢 | 本机128tile两阶段让occupancy升高却Tensor活跃下降、依赖等待增加。三阶段只在1025～1536附近部分块受益；1024/2048等完整块保留256tile。 | [NVIDIA GEMM指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)说明大tile复用与tile/wave尾部浪费的取舍；[FlashInfer b12x](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/gemm/kernels/dense_blockscaled_gemm_sm120_b12x.py)也按M/N/K/SM数量选tile与load路径。不能从“小tile适合SM120”推导所有负载都换小tile，仍需本机反例和边界验证。 |
| 打包/块宽改变输出 | 已实测FP8 Split-K关联顺序变化，FP8仍分路。后续独立近抵消oracle、宽度回归和SASS三层证据已经复现NVFP4 FullTokens FMA/尾块两次舍入；固定舍入实验进一步允许256及以上NVFP4块实际打包，九块None/DF2状态回归通过。旧输出有真实改变，含可重复数学截断反例，实验仍OFF。 | [NInfer #374](https://github.com/Neroued/ninfer/issues/374)与本机舍入因果吻合，但社区fork质量结果不代替本机反例。最新[独立诊断报告](nvfp4-dynamic-and-rounding-20261010.md)还从真实固定前缀定位第0层GDN首差异及A4后续放大；[#265](https://github.com/Neroued/ninfer/issues/265)解释record/decode求和及精度路线的影响，也报告对齐方案随权重出现正负接受收益，不能直接强制A16宣称解决拒绝。 |

社区检索另发现[#356](https://github.com/Neroued/ninfer/issues/356)/PR355讨论的是 **NVFP4 KV attention** 的split-KV，当前使用FP8 KV，不能把它当NVFP4权重GEMM优化直接吸收。FlashInfer的SM120 MoE、稀疏MLA性能报告同样不能当本机27B dense路径的收益。

GDN融合的本机因果证据已在[四组报告第11节](nvfp4-gdn-ablation-20261009.md)：共享内存由61952升到91648byte、线程从256增到512、CTA数仍96；两种续算路线都只能驻留1 CTA/SM，active warps反而16.66%→32.92%，**不能归因为occupancy降低**。原中间工作区主要命中L2，DRAM未饱和，融合减少物化并未节省同等DRAM瓶颈成本；增加的准备、同步及分块求逆/FMA顺序需分别验证。T1024组件+21.05%，仅GDN单路48K TTFT+2.15%、整请求+2.92%；双路TTFT+0.22%、整批−0.19%。没有已验证的正收益条件，保持关闭；计数器没有把每种成本精确拆开，不能将结构解释写成完整成本归因。

## 2026-10-10 续作：从测试结果追到具体机制

实际DFlash2 selector新增独立CPU条件分数核对，Huihui与原版权重各84位置均符合实际条件argmax；原版也有相同首拒绝机制。候选排序不匹配、目标端并列greedy规则、ordinary/verify数值分叉已区分，不能统称Huihui原因。完整None/DFlash2受限52批ABBA分别完成，都没确认完整长Prefill提速。真实GPU时间线定位gate/up节省被down抵消，并纠正遗漏的外层NVTX及不可相加的per-request Prefill计时口径。机制、社区原始来源、反事实和未证实项见[详细诊断](nvfp4-dynamic-and-rounding-20261010.md)。

日常安装选择舍入实验之前的r2冻结image：2×36K/256K逻辑、FP8、DFlash2 K7、Vision、Native prefix cache ON，Host18GiB pageable。HiCache、非CP GDN融合及跨lane打包保持OFF，不把数值实验binary当成服务。JSONL回到正常路径，代理自动发现2lane。经两级代理重放原两个故障请求，输出预算238904/238874未缩短，两路有输出/无返回错误，3个双lane产出采样区间，客户端取消后槽全部归还。这只是受保护的流式/取消重放，未执行工具或完成全部答案，不补两个满256K物理历史、严格质量或性能验收；启动和运行期commit保护不放宽。

进度记录必须同时回答：故障因果证据、社区已证实/仅建议的部分、我们代码差异、拟修复的语义与数值风险、测试能排除什么及还排除不了什么。新夹具不覆盖旧失败，公开报告不带私有prompt/SSE。


动态尾块及舍入缺陷的独立本机复现，见[2026-10-10专项报告](nvfp4-dynamic-and-rounding-20261010.md)。此前“普通夹具尚未复现FMA”的不确定性已由新近抵消夹具解决，但完整E2E与旧模型差异逐层归因仍未完成。
