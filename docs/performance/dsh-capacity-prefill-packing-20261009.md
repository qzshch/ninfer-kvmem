# DSH 长上下文与跨请求 Prefill：验证记录

本轮目标是修复真实 DSH 请求的容量拒绝与双路等待，使代理显示实际执行槽数，并验证跨请求 NVFP4 投影打包。每路仍是 262144 逻辑上下文、576 页（36864 token）工作窗口，FP8 KV、DFlash2 K7、Vision。不能通过缩短输出预算获得“并发成功”。HiCache 和实验 GDN 融合保持关闭。

## 验收方法

- 容量：原始数学、Jev 请求原样并发重放；用取消限制测试时间，不修改 max_tokens。检查实际两 lane 同时推进，取消后资源归还。再测试大于旧 Host 容量的历史输入及边界增长。
- 工具：保留原始 SSE 和生成文本；分别核对结构化调用、参数和异常闭合。测试不执行模型产生的命令。不能把拒绝解析错误 XML 当作修复了生成。
- 打包：默认关闭，普通执行为对照。先验证独立 lane 的 GDN/conv、KV、continuation hidden、草稿状态和 greedy Begin；再覆盖页交换、缓存、取消、Vision 回退和混合 decode。无状态投影可以合并，attention/GDN 的身份与状态不能串 lane。
- 性能：同一个二进制开关 A/B，短输入、48K 长输入、不同块大小及混合请求；报告 Prefill 总吞吐、TTFT、decode 最大暂停和有效打包次数。至少交错重复，保留负结果。
- 安全：保留用户应用和内核编译；运行期 Windows commit 余量至少 12 GiB、物理内存至少 8 GiB、GPU 余量至少 768 MiB、无显著 swap 增长。触线仅停止测试模型。

## 已确认的事故原因

日常启动命令重复指定 Host 容量，最后的 `--host-context-mib 4096` 覆盖前面的 8192。工作窗口限制的是 GPU 驻留历史，不是完整 Host 历史。全 256K 输出预算还会参与未来容量准入；两个这样的请求不能在 4 GiB 池中得到同时驻留资格。

两条实际请求已经立即通过 NAS 代理转发。后到请求在引擎中排队约 623 秒，直到前一个数学请求结束。因此，代理槽数 3 不是这次串行的根因。后续数学会话把约 149K token 历史重新提交，超过旧 Host 池的孤立输入容量。

代理已增加自动 lane 发现、真实 queueWaitMs/upstreamMs、流内错误记录及按时间保留最新请求归档。引擎 API 已提供 max_concurrency。异常工具生成增加了字节拆分解析回归；未证明生成异常已修复。

## 内存试验

6 GiB 锁页 Host 池启动测试在 Windows commit 余量约 10.36 GiB 时被保护停止，未出现 OOM。GPU 余量约 947 MiB。此结果不支持直接扩大至 18 GiB 锁页池。小型分配探针受到系统波动影响，不能据此声称确定的每 GiB commit 成本。

新增显式 `--host-context-memory pageable` 实验模式：固定容量和全部所有权、准入、字节表示不变，普通内存替代整池锁页。默认仍为 pinned。CUDA 的普通内存异步搬运可能阻塞 Host，必须验证复制完整性、生命周期、实际内存峰值和 E2E 成本后再决定日常使用。容量字段表示分配地址容量，不能当作普通内存的实际 RSS。

## 实验状态

跨 lane 打包目前合并 NVFP4 dense FFN 投影，attention/GDN 保持逐 lane 执行；最终采样、视觉输入、MTP、capture/rewrite 和稀疏查询回放边界回退普通路径。DFlash 的每行 CPU ingress 独立分配，避免异步上传未结束时被下一行覆盖。

重复未打包基线完全一致。最初将后段 FP8 FFN 合并后，1024-token 块出现状态差异：FP8 的 bulk Split-K 选择依赖总宽度，合并前后 FP32 求和关联顺序改变。现在 FP8 保持逐 lane 执行。另一个384-token案例聚合后跨越NVFP4 cp.async/TMA路由边界，也出现差异；现在仅普通路径已使用TMA的>512-token块可打包。两项失败和不合法的小块测试记录均保留，不用宽松容差抹平。

None 和 DFlash2 K7 已测试128、256、384、512、640、768、896、1024、2048九种块大小，每路输入分别为3块和3块+17 token。较小块回退，较大块实际打包。两者的 GDN/conv/tail/greedy Begin，以及有效Main KV字节和量化尺度逐字节一致；DFlash2还比较了Backend KV及完整草稿状态。None完整状态补测114.69秒通过，DFlash2 K7 137.89秒通过。分页、缓存、取消、视觉与混合decode，以及E2E性能对照仍在进行；目前不能声称吞吐收益或完整无损验收。

18 GiB pageable配置保留原数学/Jev请求输出上限238874/238904，重放记录到6个两路实际decode区间，没有流内错误。但长历史和两路满256K峰值还不能据此判定已通过。

追加完整长历史重放：原数学会话132940生成token的完整记录作为assistant内容构成派生夹具，实际149879输入token全部计算，输出1133；另一条原数学输入16917全部计算，输出1816。两者保留238874输出上限，用客户端取消限制运行时长，记录9个实际双路decode区间；约1.17秒后两级代理及Engine退休。该夹具不是已经遗失的第二轮原HTTP正文，也不是答案质量验收。

该模型稍后达到Windows commit保护线：余量10.42GiB，物理25.65GiB、GPU1687MiB、WSL约27.89GiB可用、swap0。只停止测试模型，未发生OOM；两路满256K仍未测试通过。不能因为Linux空闲或pageable启动成功就宣称整机容量安全。模型停止前后的现场采样显示commit释放约35GiB，不把这一整体差值全部归因Host池。用户应用、自定义内核、镜像网络和36GB/8GB WSL配置均保留。

服务端打包开启的短/长冷输入完成四组；两路实际各48061 token冷输入均结束。后续混合组在缓存累积后再次达到12GiB commit保护线，最终SSE连接被中断，整轮保持失败状态。停止前Host记录occupied约5.15GiB、KV4.14GiB、五个Host状态；这些仍有所有权，不能据此断言泄漏。后续将关闭跨请求缓存的计算A/B与开启缓存的生命周期/回访验证分开，保留本轮失败，不将降配结果混入同配置成绩。

测试工具两项失败也保留：长历史runner首次误把SSE空role事件当首token，尚未完成Prefill即取消；服务端runner首次误把Engine的stop_token当作协议stop而拒绝。修正夹具后使用新证据目录重跑，未覆盖原失败。cache mode explicit只关闭隐式写入提示，不能保证已发布前缀不会读取；冷对照必须核对实际hit=0。

两级代理发现并修复取消遗漏：一个close回调先释放槽位，后一个见已结束而未关闭上游连接。回归在修复前失败，修复后连续3次取消可关闭两级上游。真实数学请求取消后0.281秒引擎归零并记录cancelled，输出上限保持238874。测试必须同时等待代理和引擎退休。

代理410c245已隔离提交Native与可选缓存参数支持，11项针对暂存内容的参数、开关和错误测试通过。pageable模式与统一Host额度可以往返；旧HiCache增强二进制不接收不支持的内存参数。这不等于完成整机容量或HiCache验收。

GDN 融合在本机此前 T256～4096 的组件测试中没有确认正收益，且改变了部分表示状态。继续默认关闭。要成为正收益，省下的搬运/启动成本必须超过重复准备和同步成本；目前没有已验证的正收益配置。
